## the meter — remaining work

The model (`quantity(item, time)`, one append-only log, totals computed not stored) is live for both item types; see `AGENTS.md`. What's still open:

- [ ] **capacity is a count, not a difference (the pool boundary)** — `net = default − scheduled` is **boolean coverage**: right for a quantity-1 unit (a specific room / seat), but for a **pool** (N of a type) `−` *deletes* an interval instead of decrementing — two overlapping bookings would silently vanish a unit that still had N−2 free. A pool of rooms is N rows, one per unit (multiplicity), which is why the live engine is safe. A **large fungible** pool (parking spaces, GA seats) is where rows stop paying: that path is **coverage-counting** — `remaining(t) = capacity − overlaps(t)` over an interval→count map (`portion.IntervalDict`), available where `remaining > 0`. A distinct mechanism that **must not reuse `−`**; build it as its own function, don't extend `availability.py`'s.
- [ ] **an item offers exactly one pattern** — `availability_rule` is one RRULE and `availability_duration` one number, so "Mon–Fri 6am–2pm and Sat 8am–12pm" (two different durations) cannot be expressed. RFC 7953 VAVAILABILITY is the shape: an envelope holding N AVAILABLE sub-components, each with its own DTSTART + DURATION + RRULE. The existing pair is the one-element case, so migration is mechanical. The envelope also bounds a seasonal offer, and a real DTSTART fixes a second bug — `availability.py:84` anchors on the QUERY WINDOW (`rrulestr(rule, dtstart=ws_l)`), so any rule whose phase comes from DTSTART (`INTERVAL=2`, alternating weekends, a three-day cycle) answers differently depending on the day you ask.
- [ ] **the cache is written before the log** — `manage_stock` (op: move) gates + updates the scalar `quantity`, then appends the movement. A rare append failure would leave the cache ahead of the log. Log-is-truth ordering is append-first, then materialize; and a `rebuild_cache` (fold the log → set the scalar) is the reconciler, which is also what makes truncation-to-S3 safe and what a fresh cache would be seeded from. Capacity has no such gap — it has no cache, it only folds.
- [ ] **fold-reads for stock** — `manage_stock` (op: get) / `oob_inventory` read the cached scalar (O(1), correct). The fold (`movements.item_on_hand`) is the authority and is what a reconciler / an as-of read (`on_hand(t)`) would use; expose it when turnover or an audit read needs it, rather than making the hot path O(log).
- [ ] **archive** — the log is append-only and grows; truncate periodically to **S3 + Athena** (the historical physical-i/o series for turnover / working-capital / the public feed). Safe once the cache is rebuildable, since current totals are materialized.

## capacity consumers (inherited from calendar)

Availability-as-**quantity** lives here; time-as-**trigger** stays in `modules/calendar` (its `events` table + the EBS Scheduler / agent-dispatcher — "do X at time T"). Calendar's availability half is **removed** (its `scheduled` + `availability` tables and `manage_availability` / `get_availability` / `reserve` tools are gone). Its consumers land here:

- [ ] **`labor` becomes a consumer** — an employee is a capacity item (`unit_price` = the sell/bill rate; the wage `rate` stays in `labor`, keyed to the `worker` row). Booking a worker's time is a `@period` movement like any other unit (`source=shift:<id>`; the consumer composition is `AGENTS.md` § the source is the consumer).
- [ ] **agent-poke availability loop** — a weekly cron → the agent emails/chats each employee "availability next week?" → the reply sets their capacity item's `availability_rule`. Availability collection with zero forms.
- [ ] **utilization on the public feed** — `reserve` (op: availability) returns `utilization` per item; the unit-economics number the public feed most wants (occupancy, bay utilization) still needs an oob surface, alongside the turnover read.
- [ ] **concurrent booking guard** — `reserve` checks the fold then appends; two simultaneous bookings for the same interval could both pass. Calendar's `reserve` guarded this with a conditional `TransactWriteItems` (a `rev` on the offer row) — that doesn't carry over, since the log has no offer row to condition on. A guard needs a per-item lock row (conditional write on a `version`) or a conditional put keyed on the interval. Real for a public booking page; not for an agent-mediated one.
- [ ] **pool + multi-resource reserve** — pick-a-free-unit-and-retry inside the op; multi-resource (a worker AND a bay, both guarded in one transaction). Depends on the guard above and, for large fungible pools, on the coverage-count layer.
